# GitHub README 产品叙事设计

## 目标

把仓库首页从“面向开发者的目录和合同说明”改成“产品优先、开发完整”的中英文公开入口。

README 首先让旅行者、生活方式主理人和潜在贡献者理解：`interactive-trip-planner` 能把个人品味、当地资料和现实约束组合成一份可信、舒服、可以继续修改的旅行计划；随后再提供安装、数据结构、贡献和验证信息。

本次仍发布为 `0.1.0`。它是可以用于真实规划和继续迭代的开发者预览版，不宣称已达到全球数据源完整覆盖的 Public V1。

## 受众顺序

1. 想获得个性化旅行方案和交互地图的旅行者。
2. 想分享选店逻辑、生活品味或满意行程的主理人。
3. 想贡献 Taste Model、地区来源包、当地语言词库和视觉主题的开发者。
4. 需要理解构建、验证和 REDSkill 发布边界的维护者。

README 不假设读者已经理解 Codex Skill、Regional Source Pack、JSON CLI 或 contract。专业名词第一次出现时先用产品语言解释，再给出技术名称。

## 语言结构

- `README.md` 是默认中文首页。
- `README.en.md` 是英文产品页。
- 中文页顶部显示 `**中文** | [English](README.en.md)`。
- 英文页顶部显示 `[中文](README.md) | **English**`。
- 两个版本共用同一张公开西班牙截图，保持相同的章节顺序、能力事实、0.1 边界、安装方式和贡献入口。
- 英文版使用自然的产品英语表达，不逐句机械翻译中文；任何产品承诺不得比中文版更强。

## 核心产品承诺

主标题采用：

> Interactive Trip Planner — 把你的生活品味带到陌生城市

英文页采用：

> Interactive Trip Planner — Bring your taste in everyday life to a city you've never visited

首屏说明采用结果导向表达：

> 它不只是生成景点清单，而是根据你想怎样旅行，结合当地语言资料、代表性景点、社区生活和现实营业信息，安排成一条舒服、可信、可以继续修改的路线。

首屏只传达四件事：

- 不用先知道该去哪里，Skill 会根据目的地和旅行方式推荐适合的品味方向。
- “想体验 local”不会自动排除第一次到访值得看的代表性景点。
- 每个进入路线的地点都要解释去做什么、看什么、为什么适合这次旅行。
- 最终交付是可增删、改顺序、按日期浏览的交互地图，而不是一次性文字清单。

## README 信息架构

以下结构同时适用于 `README.md` 和 `README.en.md`。

### 1. Hero

包含产品标题、两句说明、一个最短使用示例，以及西班牙 Market Roof 地图的干净截图。

截图使用公开样例数据，不出现真实订单、航班、酒店预订、姓名、账号或本地文件路径。图片建议放在 `docs/assets/readme/spain-market-roof-map.png`，README 使用相对路径和说明性 alt text。

### 2. 它和普通 AI 攻略有什么不同

用结果对比解释六项能力，不先展示内部模块名：

| 常见攻略 | Interactive Trip Planner |
| --- | --- |
| 根据热门榜单拼景点 | 先理解旅行方式和取舍，再筛地点 |
| 只使用中文或英文搜索 | 根据目的地生成当地语言检索任务 |
| “local”与著名景点二选一 | 第一次到访时平衡城市代表性与当地生活 |
| POI 只有泛泛推荐语 | 说明到现场做什么、看什么和地点故事 |
| 按热度堆满一天 | 按街区、时间、体力和夜间安全安排动线 |
| 输出静态文字 | 输出可继续加入、移除、排序和保存的交互地图 |

### 3. 你最终会得到什么

用交付物而不是组件描述产品：

- 一份明确旅行主线和节奏的行程简报。
- 一个经过来源筛选的 POI 候选池。
- 每天 1–3 个主要锚点和同街区吃喝、休息、替换选项。
- 节庆、展览、闭馆、预约和临近复核提醒。
- 一张保留全程总览、每日顺序和编辑状态的交互地图。

### 4. 从品味到陌生城市

再引入 `Hybrid Taste Model`：它不是某位主理人的固定路线，而是可迁移的选择逻辑，由正向偏好、反偏好、节奏、选店标准、路线原则、数据源偏好和视觉语言组成。

说明用户可以：

- 直接使用官方模型。
- 让 Skill 根据目的地和旅行方式推荐模型。
- 用自己的满意行程和选择逻辑贡献新模型。

### 5. 当地语言和数据源

以搜索漏斗解释，而不是先罗列 CLI：

1. 官方来源确认票务、营业、节庆和交通事实。
2. 当地语言检索发现本地媒体、论坛和生活方式讨论。
3. Taste Model 筛选与用户品味相符的地点。
4. 对进入路线的候选重新核对近期、官方和可追溯资料。
5. 有冲突或临近变化的内容明确标注复核时间。

随后说明当前 0.1 覆盖：Global Base、中国大陆、日本、法语区来源包，以及西班牙语和加泰罗尼亚语检索词库。明确西班牙尚未拥有独立 Regional Source Pack。

### 6. 如何开始

先给一句自然语言调用示例，再区分两个安装面：

- Codex / GitHub 完整版：安装 `skill/`。
- 小红书 REDSkill：使用 `releases/redskill-0.1.0/interactive-trip-planner/`。

安装说明只保留必要步骤，构建和仓库布局移到后文。

### 7. 0.1 能力与边界

使用普通产品语言说明：

- 已可用于有人监督的真实旅行规划、来源研究、路线设计和地图生成。
- 不保证所有国家已经有专属地区来源包。
- 社媒和论坛用于发现与体验线索，不作为营业时间、票务和安全事实的唯一证据。
- 节庆、营业、价格、交通和预约仍需临近出发复核。
- Public V1 的评估要求链接到详细文档，不在首屏使用 `contract slice` 等内部表达。

### 8. 贡献自己的品味与地区知识

为非开发者和开发者分别给入口：

- 主理人贡献：满意行程、选择理由、反偏好和可迁移原则。
- 地区贡献：来源包、当地语言词库、论坛/媒体发现入口和验证优先级。
- 设计贡献：地图主题和目的地 preset。

贡献内容最终落到版本化文件，并继续通过仓库验证，不把自由文本直接当成可信事实。

### 9. 开发、验证与仓库结构

把现有 README 的目录、CLI、`npm test`、REDSkill 构建和隐私边界保留在末段。Discovery CLI 使用折叠说明或链接到详细参考，首页只解释其用途。

## 产品文案原则

- 先写用户能得到什么，再写内部如何实现。
- 每个专业名词第一次出现时给一句自然语言解释。
- 不用“全网最好”“完全 local”“自动保证正确”等无法证明的宣传语。
- 0.1 的限制与价值同时出现，不用免责声明淹没第一屏。
- 不把榜单、论坛或社媒描述为事实真值源。
- 不把 Taste Model 描述成复制某个人的具体消费记录；它表达可授权、可迁移的判断逻辑。

## 验收

### README 内容

- 第一屏不出现目录结构、CLI 或 contract 术语。
- 读者在前两个章节内能回答“产品解决什么问题、与普通攻略有什么不同、最终得到什么”。
- 安装、贡献、0.1 边界、数据源策略和技术验证均有明确入口。
- 两份 README 中的版本、目录、命令和产品事实与当前代码一致。
- `README.md` 与 `README.en.md` 顶部可以互相切换，并保持相同章节顺序。
- 两份 README 的所有相对链接和图片路径有效。

### Skill 与发布包

- `npm test` 全量通过。
- `releases/redskill-0.1.0/interactive-trip-planner/` 根目录包含 `SKILL.md`。
- REDSkill 不包含 YAML、图片、压缩包或其他不支持格式。
- 示例和截图不包含个人路径、订单、航班、酒店或身份信息。

### GitHub 发布

- 只提交本轮确认的 0.1 文件，不带入 `.superpowers/`、`experiments/` 或私人旅行材料。
- 推送 feature branch，并以 `main` 为 base 创建 draft PR。
- PR 说明包含产品变化、0.1 边界、验证命令和 REDSkill 上传入口。
